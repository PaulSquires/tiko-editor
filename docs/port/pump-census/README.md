# The pump oracle — captures

Which filter claimed which message, counted from the running editor. Generated by
`TIKO_PUMP_TRACE=1` — see `src/modPumpTrace.bi` for what it records and what it deliberately
does not.

```bash
set TIKO_PUMP_TRACE=1 && tiko.exe
```

The summary is written at process exit to `pump-trace.txt` beside the exe. That file is
**gitignored**: it is the last run, not evidence. Captures that a census cites are copied in
here by hand, named, and described below.

**Why this exists.** `frmMain`'s pump is twelve ordered filter claims, three accelerator tables
and an `IsDialogMessage`, each with a comment explaining what it claims and why it sits where it
does. Those comments are the best documentation in the codebase and they are still only a claim
*about* the code. A filter that never fires cannot be verified as ported — the port would be
equally green whether it reproduced the behaviour or dropped it.

---

## `run-1-undivided.txt` — 2026-08-10, first driven session

Ordinary editing plus the Options, Themes and About dialogs. **5517 messages through
`frmMain`**, 191 through `frmOptions`, 104 through `frmThemes`, 170 through `frmAbout`.

**READ ITS `IsDialogMessage` NUMBER WITH THE CORRECTION BELOW, NOT AS IT STANDS.** This capture
predates the keyboard/other split and its headline invites precisely the wrong conclusion.

### The correction, which is the most useful thing this capture produced

It reads `IsDialogMessage claims 4115` against 5517 — 75% — which looks like a very large hole,
since `IsDialogMessage` is the one Win32 mechanism in the chain with no PsPlatform analogue.

It is not a hole. **`IsDialogMessage` DISPATCHES what it processes.** The API contract is
explicit that a message it handled must not then be passed to `TranslateMessage` or
`DispatchMessage`, so a TRUE return means *"I was the dispatcher"*, not *"I swallowed it"*.

The capture says so itself, and this is why the number was not taken at face value: its claim
list contains `WM_PAINT`, `WM_TIMER`, `WM_MOUSEMOVE` and `WM_LBUTTONDOWN`. Had those been
swallowed, the editor would not have repainted — and it repainted throughout.

So an undivided count measures message volume and nothing else. The quantity the port needs is
the **keyboard share**, because dialog-key semantics — Tab traversal, the default button,
Escape — are the part with no analogue; everything else it claims is dispatch that
`surf.Dispatch` already does. `PumpTrace_NoteTerminal` splits the pair from run 2 onward.

### What it establishes regardless of the split

**Eight of `frmMain`'s twelve filters never fired at all.** Absent from the capture:
`handleMouseShowScrollBar`, `PsMenuBar`, `ContextMenu`, `PsTextBox`, `Codetip`,
`handleCtrlSpaceAutoComplete`, `handleAltKeyMenuBar`, `handleKeysFindReplace`.

**That is a fact about the session, not about the code**, and the census must carry it as
*unexercised*, never as *dead*. A context menu was not opened; Alt was not pressed; the Find bar
was not used. The four that did fire, fired rarely — `frmAutoComplete` 5, `PsListTree` 2,
`frmExplorer` 1, `handleEscKeyModeless` 1.

**The accelerator tables are close to unused.** `accel:main` claimed **4** messages in the whole
session — `Ctrl+S`, `F2`, `T`, and one OEM key. `accel:usertools` and `accel:buildconfig` never
fired once. Three stacked `HACCEL`s, and two of them are cold.

**`frmExplorer` and `PsListTree` both claimed `VK_RETURN`/`VK_F2`** — the two filters whose
comments say they exist to beat `IsDialogMessage` and the accelerator chain to those exact keys.
Their comments are corroborated by the trace, which is worth recording because most of the
others' are not yet corroborated by anything.

## `run-2-split.txt` — 2026-08-10, driven at the cold paths

The same editor plus Options, About and User Tools, with the gestures run 1 missed: menubar
keyboard navigation, Alt mnemonics, Tab and Shift+Tab traversal, Ctrl+Space, the Find bar.
**7167 messages through `frmMain`**, 1614 through `frmOptions`, 323 through `frmUserTools`, 127
through `frmAbout`.

Carries the keyboard/other split, and it settles the question run 1 could only raise:

| pump | messages | `IsDialogMessage` keyboard | share |
| --- | --- | --- | --- |
| `frmMain` | 7167 | 53 | **0.7%**, and visibly ordinary typing |
| `frmOptions` | 1614 | 87 | 5.4%, and visibly Tab/arrow/Enter traversal |
| `frmAbout` | 127 | 7 | 5.5%, traversal |

`DispatchMessage:KEYBOARD` is **zero in every pump** — every keyboard message reaching the end of
a chain went through `IsDialogMessage`. See [`../pump-census.md`](../pump-census.md) for what
follows from that.

Five claim points fired here that were silent in run 1: `PsMenuBar` (17),
`handleCtrlSpaceAutoComplete` (1), `handleKeysFindReplace` (2), and `accel:main` picked up the
Alt mnemonics. **Eight claim points have now fired in neither session** and are carried as
unexercised, not dead.

**The completeness check passes.** Claims plus terminal outcomes account for 7166 of `frmMain`'s
7167 messages, 1612 of `frmOptions`' 1614, 126 of `frmAbout`'s 127 and 323 of 323 — the one or
two missing per pump being the message the loop exited on. A chain that leaked would show it
here.

## What a capture cannot tell you

**Absence is not evidence of deadness** — see above. It is the single easiest misreading of this
directory and the reason every claimant count is reported against what the session did.

**The sample list is capped** (`PUMPTRACE_MAXSAMPLES`). A slot that hit the cap says so in the
capture. Run 1 hit it on `frmMain`'s `IsDialogMessage` at 12; the cap is 24 from run 2.

**Ordinary editing under-exercises dialogs.** Reaching a filter usually means using the feature
it guards, so a capture intended to cover the chain has to be driven deliberately rather than
naturally.
